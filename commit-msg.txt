fix: hourly bar affichait des donnees de l'heure suivante

Le user a signale que "les donnees meteo disent n'importe
quoi" dans la barre horaire. Cause identifiee :

openMeteoToInternal decoupeait hourly en cherchant le
premier index avec un buffer de 30 min en arriere :
  if (h.time[i].getTime() >= nowMs - 30min) include

A 10h42 par exemple :
  nowMs - 30min = 10h12
  h.time[10] = "10:00" -> 10h00 < 10h12 -> EXCLU
  h.time[11] = "11:00" -> 11h00 >= 10h12 -> INCLUS

L'array hourly decoupe commencait donc a 11h00 au lieu
de 10h00. Ensuite dans renderCity, le nowIdx etait
calcule par comparaison de timestamps :
  - cur.time = "10h42"
  - hourly[0] = "11h00" (premiere entree)
  - Aucune entree <= curMs (10h42) dans hourly
  - nowIdx = -1 -> fallback a 0

La cellule "Maint." affichait donc hourly[0] = "11h00"
avec le label "Maint." -> completement faux ! A 10h42
on voyait les donnees de 11h00 presentees comme
l'observation courante.

Cas les plus problematiques : toute heure > H+30 (10h42,
14h55, 23h45, etc.) affichait les donnees de l'heure
SUIVANTE, pas de l'heure courante. D'ou les "donnees
disent n'importe quoi".

Fix : elargir le buffer a 120 min (2h). Open-Meteo a
des entrees sur l'heure pile, donc :
  - Pire cas = 10h59 : nowMs - 2h = 8h59 -> inclut h.time[9] = 9h00
  - Toutes les autres heures : au pire cas inclut h.time[10] = 10h00

Avec 2h de buffer garanti, hourly contient toujours
l'heure courante ET les 2h precedentes en memoire. Le
code de rendu (deja corrige precedemment) utilise une
comparaison de timestamps pour positionner maintenantIdx
sur l'entree la plus proche <= curMs, donc la cellule
"Maint." pointe toujours sur l'heure courante reelle.

Verification tracee pour 10h00, 10h29, 10h42, 10h59,
11h00 : dans tous les cas nowIdx pointe sur l'entree
10h00 quand curMs est dans [10h00, 11h00[.
